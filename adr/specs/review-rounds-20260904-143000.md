# Spec: Review rounds and the "since my last review" diff

Date: 2026-09-04 · Status: draft for alignment
Intent: `adr/intent-focused-pr-review-20260904-143000.md`

## Summary

A reviewer sends feedback. The agent edits the code or the document. The reviewer
must then read only what the agent changed. Today the reviewer reads the whole
change again.

This spec records what the reviewer saw at each send. It adds a diff that compares
that record against the current state.

This spec serves both pull request review and document review.

## The problem

Plannotator tracks freshness, not history. `currentSnapshotId()` in
`packages/server/review.ts` changes whenever the diff changes. A client echoes the
id back so the server can detect a stale view. The id lives in memory. Nothing
records the content behind it, and nothing survives a restart.

So the app can answer "is your view stale?". It cannot answer "what changed since
I last reviewed?".

## The model

A **review round** is one complete pass: the reviewer opened a diff, wrote
annotations, and sent feedback. The round records what the reviewer saw.

```ts
interface ReviewRound {
  id: string;                 // uuid
  createdAt: number;
  /** What was under review — mirrors AgentJobDiffContext. */
  diffContext: { mode: string; base?: string; label?: string };
  /** Merge-base commit at send time. Tells an agent edit from a base move apart. */
  baseCommit?: string;
  /** Content identity per file at send time. */
  files: ReviewRoundFile[];
  /** Annotation ids sent in this round, so a later round can show what they caused. */
  annotationIds: string[];
}

interface ReviewRoundFile {
  path: string;
  /** git blob id of the content the reviewer saw. */
  objectId: string;
}
```

The `objectId` is the anchor, not a line range. Line ranges move. A blob id names
exact bytes, and git can diff two blob ids directly.

`packages/shared/review-core.ts:1108` already computes a `workingObjectId` per
file for the staleness fingerprint. Reuse it. Do not add a second way to identify
file content.

For a document review the file is not always tracked by git. Fall back to a SHA-256
of the file bytes, and store the bytes alongside the record, because an untracked
document has no other copy of its past state.

## Storage

Mirror `packages/shared/guide-store.ts` exactly. It solved this problem already.

```
${PLANNOTATOR_DATA_DIR}/rounds/{repo-key}/{id}.json      the round record
${PLANNOTATOR_DATA_DIR}/rounds/{repo-key}/{id}/          stored bytes, documents only
```

Follow its rules: the same `repo-key` derivation, atomic writes through tmp and
rename, and a corrupt file loads as "no saved round" rather than an error. Keep
the module runtime-agnostic and vendor it to Pi through `vendor.sh`.

Warning: a document round stores file bytes. Cap the stored size and drop the
oldest rounds past a limit. An uncapped store grows without end.

## The diff mode

Add `since-review` to the diff types, beside the `since-base` mode that ADR 005
introduced. It compares the last round's recorded content against the current
content.

- The left side is the round's `objectId` per file, read with `git cat-file`.
- The right side is the current content, exactly as `since-base` reads it.
- A file absent from the round is wholly new to the reviewer. Show it in full.
- A file in the round but absent now is deleted. Show the deletion.

Follow the `since-base` integration list in
`adr/decisions/005-since-base-github-view-default-20260701-223706.md`. That change
named every seam a new diff type must touch: `runGitDiff`,
`getGitDiffFingerprint`, `getFileContentsForDiff`, `getGitContext`,
`GIT_DIFF_TYPES`, `canStageFiles`, and the client parse in `App.tsx`. Use it as
the checklist.

## When a round is written

Write the round when the reviewer sends feedback, not when the agent finishes. The
round records what the *reviewer* saw. The agent's later edits are the thing being
measured.

## What the reviewer sees

On reopening a review that has a prior round, the app opens on `since-review` and
the header names it: `Since your review · 2 hours ago · 4 files`.

One control switches back to the full change. The reviewer must always be able to
reach the whole diff, because a partial view hides regressions in code the agent
did not touch this round.

When no prior round exists, nothing changes. The app opens on `since-base` as it
does today.

## Test first

**Unit — `packages/shared/round-store.test.ts`.** Mirror `guide-store.test.ts`:
write and read back a round, a corrupt file loads as absent, two repositories do
not collide, and the size cap drops the oldest round.

**Integration — round trip on a fixture repository.**

1. Create a branch that changes files A, B, and C.
2. Record a round.
3. Edit file B only.
4. Ask for `since-review`. Assert the result holds file B alone.
5. Add file D. Assert `since-review` holds B and D.
6. Delete file A. Assert `since-review` shows A as deleted.

**Integration — the base moves.**

1. Record a round on a branch.
2. Commit a change to file E on the base branch, then merge the base in.
3. Ask for `since-review`. Assert file E is hidden, and the hidden count is 1.
4. Now edit file E on the branch as well. Assert file E appears in full.

**Manual — Playwright checklist.**

1. Open a review, comment, send feedback.
2. Let the agent edit one file.
3. Reopen. The header reads `Since your review`, and the tree holds one file.
4. Switch to the full change. Every file returns.

## Decided — a moving base

`since-review` shows the agent's edits only. It hides changes that came from the
base branch.

Decided 2026-09-04. The reviewer read this diff to answer one question: what did
the agent do about my comments? Upstream commits do not answer it.

**How to tell them apart.** Record the merge-base commit in the round, beside the
per-file blob ids. At diff time, resolve the current merge-base. A file's change
comes from the base alone when both of these hold:

1. The round's recorded `objectId` equals the file's blob at the old merge-base.
2. The file's current content equals its blob at the new merge-base.

Then the reviewer saw the old upstream content and now sees the new upstream
content, and nothing else touched the file. Hide it.

When only one condition holds, the agent and the base both touched the file. Show
the whole file change. Never try to split one file's diff into two sources. A
partial diff of a single file misleads more than a full one.

**Never hide silently.** The header names the count, in the same manner as the
source-only diff: `Since your review · 4 files · 12 hidden from main`. One control
shows them. A reviewer who cannot see that a merge happened cannot judge it.
